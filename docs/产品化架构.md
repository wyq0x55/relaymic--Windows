# RelayMic 产品化：服务端架构与仓库策略

2026-08-17 整理。前提：走全球订阅路线（见 商业化.md 路线 A）。

## 一、服务端选型：Cloudflare 全家桶，起步零 VPS

| 组件 | 方案 | 成本 |
| --- | --- | --- |
| 官网 / 落地页 / 文档 | Cloudflare Pages | 免费 |
| 信令 + 配对码（撮合、交换 SDP）| Workers + Durable Objects（配对码状态天然适合 DO）| $5/月 |
| **TURN 中继** | **Cloudflare Realtime TURN**（anycast 就近接入，免运维）| **前 1000GB/月 免费**，超出 $0.05/GB |
| License / 订阅状态 | Workers KV / D1 | 免费额度内 |
| 支付 | Paddle / LemonSqueezy（MoR 兜全球税务）| 抽成 ~5% |

## 二、中继成本账（订阅毛利的底）

```
音频 96kbps ≈ 43MB/小时
重度用户（每天 2h、100% 走中继）≈ 2.6GB/月
1000GB 免费额度 ≈ 385 个全中继重度用户；
实际多数连接打洞直连（零中继流量）→ 免费额度撑到千级用户
超额后：每重度用户 $0.13/月 vs 订阅 $4.99 → 毛利 ~97%
```

自建 VPS 的时机：中继月流量稳定超过几 TB（几千付费用户）时，
多区域 coturn（Hetzner €5/月含 20TB）比 $0.05/GB 省。TURN 是标准协议，
切换 = 改一下下发配置，无痛。

## 三、多 Mac 的流量模型

- **发送端上行 = 台数 × 96kbps**（编码一次、每台独立发一份）：
  3 台 288kbps、5 台 480kbps —— 任何家宽无压力
- **中继账单 ≠ 台数倍**：每条连接独立决定直连/中继，只有打洞失败的
  连接计费。最坏情况（全走中继）3 台 ≈ $0.39/月，毛利仍 92%
- license"个人最多 3 台 Mac"既是条款也是成本护栏
- 未来优化（量大再说）：Cloudflare SFU —— 发送端只发一份，SFU 分发 N 台，
  TURN↔SFU 之间流量免费；代价是放弃 P2P 直连。个人 ≤3 台没必要，
  出现"一人广播十几台"的团队场景再切

## 四、中国用户：CF 打底 + 国内 VPS 增强，ICE 自动分流

**分流不用写代码 —— ICE 协议天生干这个**：`/ice-config` 下发多组 TURN，
客户端对所有路径做连通性检查、自动选 RTT 最低的：

```json
{ "iceServers": [
    { "urls": "turn:turn.cloudflare.com:3478", ... },
    { "urls": "turn:cn.relaymic.com:3478", ... }
]}
```

- 中国用户：国内 VPS 20~50ms < CF（绕港/日边缘）100ms+ → 自动走国内
- 海外用户：反之自动走 CF；任何一组挂了自动容灾
- 规模大后升级为按地域下发：Workers 里 `request.cf.country == "CN"` 一行代码
- **现有阿里云 coturn（139.224.x.x）直接转正为中国区生产节点**

三个注意点：
1. 信令国内可达性：workers.dev 被干扰，必须自定义域名 + CF 代理；
   要求更稳时国内 VPS 加信令入口 + DNS 地域解析（起步不必）
2. **TURN 凭证改短时签发**：coturn 换 `use-auth-secret`，Workers 按订阅
   状态签限时凭证。静态密码商用等于把中继送人当公共代理
3. 备案：国内 VPS 跑 TURN（纯 UDP）不需要备案；只有官网想走国内加速
   才涉及，初期国内用户直连 CF 页面即可

## 五、仓库策略：新开产品仓库，现仓库转为自用上游

**决策：不在现仓库里做产品化，新开 RelayMic 产品仓库（从当前代码
快照开始、不带 git 历史）。**理由：

1. **历史污染**：现仓库 git 历史里有 TURN 密码、真实 IP、个人环境 ——
   产品仓库迟早给协作者/审计/部分开源看，第一天干净比事后洗历史便宜得多
2. **身份分离**：现仓库是你的**自用生产系统**（三台 Mac 天天在跑），
   产品化的破坏性改动（module 改名 relaymic、i18n 抽取、去 hardcode、
   加 license 校验、配对码接入）不该威胁它的稳定
3. **改动是结构性的**：在跑着生产的仓库里换引擎，两头都做不好

迁移方式：
- `internal/audio`、`internal/rtc`、`internal/sender`、接收端/网页核心 → 原样搬
- `deploy-fleet.sh`、个人 docs、写死的参数 → 不搬
- 新增（产品仓库独有）：Workers 信令/配对码、Mac 菜单栏 App + 签名安装器、
  i18n、license 校验、支付对接
- bug 双向流动：初期手动 cherry-pick 即可，不搞 submodule/monorepo 过度工程

时机：**落地页投流测试不需要动任何代码** —— 测试过线、真开工的第一件事
才是开新仓库。测试不过线，连仓库都省了。
